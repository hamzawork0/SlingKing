01

What I understand you are asking for

One inventory ledger, many ways to sell out of it — and enough recorded history that a profit number computed today still holds next year.

The workspace at C:\Hamza Projects\SlingKing is empty. Nothing exists yet: no solution, no git repository, no prior schema. This is a greenfield build with no migration or compatibility burden.

The system's centre of gravity is not orders and it is not products — it is the inventory ledger. Every other module writes into it or reads from it. Getting that ledger's invariants right is what the whole build stands on, which is why the plan below front-loads inventory and defers everything that merely reports on it.

The four things the design has to get right

  • Stock is derived, not stored. A mutable current_stock column drifts. The truth is an append-only transaction ledger; the fast-read numbers are a projection guarded by database constraints and reconcilable against the ledger at any time.
  • Costs are layered, not averaged. FIFO means every unit in stock carries the price you actually paid for it, and every sale records precisely which of those units it consumed. That record is what makes historical profit immune to later price changes.
  • Reservation is separate from consumption. Confirming an Instagram order must protect stock without removing it; only delivery removes it. Two different quantities, two different transaction types, one atomic guard against overselling.
  • Channels are data, not code. Instagram, WhatsApp and Offline differ by configuration rows, not by branches in the order service. Meesho and Flipkart later become an adapter plus a row — not a change to any core module.

02

Issues and ambiguities before a line is written

Both blockers are now answered and closed below. The rest I have decided with a stated default — overturn any of them and I will adjust.

Were blocking — now resolved

B1

Cost price is entered per SKU, per entry — and the field is optionalResolved

Cost is captured on each opening-stock row and each purchase line, so two intakes of the same SKU at different prices remain two layers and the FIFO queue works as designed. A single editable “cost price” on the variant was considered and rejected: changing it later would silently rewrite the profit on every past sale.

The field is optional. A blank cost opens the layer with unit_cost = null, which means unknown, never zero. Quantities, reservations and the oversell guard are untouched — only money is affected, and the system reports the gap rather than hiding it. Section 06 covers how consumption, backfill and report coverage handle an uncosted layer.

AnswerCost price per SKU per entry, optional; uncosted units are surfaced, not assumed free
B2

GST is out of scope entirelyResolved

No tax fields anywhere: not on purchases, purchase_items, orders or order_items, and no tax_treatment column on sales_channels. Every price and every cost is a single final amount. A cost layer holds exactly the number that was typed, with no ex-GST arithmetic to get backwards.

This removes columns from the design rather than adding them, and it is why the schema below is simpler than the first draft. When Meesho and Flipkart integration arrives after Release 2, GST returns as an additive migration — HSN codes, tax rates, a channel tax treatment — scoped and costed as its own piece of work rather than smeared through Release 1.

AnswerNo GST modelling in either release; revisit at marketplace integration

Decided with a default — say the word to change any

D1

Revenue and COGS are recognised on delivery, not on order dateDecided

An order confirmed on 28 March and delivered on 2 April counts in April. Cost and revenue must land in the same period or gross profit is nonsense, and the cost is only knowable once the FIFO layers are consumed at delivery. Every financial report therefore filters on completed_at, while operational lists filter on order_date.

D2

Shipping charged to the customer is not product revenueDecided

Gross Profit = product revenue after discounts − FIFO COGS. Shipping collected shows as its own line and rolls into net profit; shipping paid is a Shipping expense. Folding courier charges into revenue would flatter your product margin, which is the one number you will actually make buying decisions on.

D3

Order-level discount is allocated pro-rata across linesDecided

You asked for product-wise and variant-wise sales reports. A ₹300 discount sitting only on the order header cannot be attributed to any product, so those reports would silently overstate every line. Each order item stores an allocated_order_discount computed by line share at completion, with the rounding remainder pushed onto the largest line so the parts always sum exactly to the whole.

D4

Returns reverse the original FIFO consumption — they do not create a new layerDecided

Restocking a return as a fresh layer at today's cost would let you launder margin: sell cheap stock, return it, and it reappears valued differently. Instead the consumption records for that order item are reversed newest-first, quantity flows back into the exact layers it came from, and COGS is credited at the exact rate it was charged. The restored units keep their original position in the FIFO queue, which is also just correct.

D5

Damaged returns are restocked, then immediately written offDecided

Rather than a special cost path, a return marked Damaged runs the normal reversal and is then consumed straight back out as a Damage transaction in the same database transaction. Revenue reverses, COGS reverses, and the loss lands in its own bucket where you can see it — instead of quietly deflating your product margin.

D6

Partial fulfilment is out of scope; partial returns are inDeferred

Your brief says "handle partial order fulfilment carefully if implemented". Splitting one order into several shipments means split reservations, split FIFO consumption, and per-shipment status — roughly a doubling of the order module for a case a single-operator Instagram shop rarely hits. Orders ship whole; lines can be removed while Draft or Confirmed. Partial returns are fully supported, as specified.

D7

Shipped can be cancelled; Delivered cannotDecided

An RTO happens after dispatch and before physical stock has moved, so Shipped → Cancelled simply releases the reservation. Once Delivered or Completed, stock and cost have moved and the only correct instrument is a Return — cancellation is blocked, so you can never erase a completed sale from history.

D8

Your payment status list has a gap: partial refundsAmended

Pending / PartiallyPaid / Paid / Refunded cannot express "paid ₹3,000, refunded ₹800 for one returned item" — the common outcome of a partial return. I am adding PartiallyRefunded. Status stays fully derived from the payment rows; there is no editable status field anywhere.

D9

An upward stock adjustment always opens a layer, costed or notAmended

The system-wide invariant is SUM(layer.remaining_qty) = physical_qty per variant. An adjustment that increases stock without creating a cost layer breaks it permanently, and every FIFO calculation after that point is wrong. Upward adjustments therefore always open a layer — but in line with B1 the unit cost on it is optional, and a blank one leaves the layer uncosted rather than blocking the adjustment. The quantity invariant holds either way; only the valuation is deferred. Downward adjustments consume FIFO like any other outflow.

D10

Offline orders never reserveDecided

Reservation exists to hold stock between a promise and a handover. Across a counter there is no gap, so Draft → Completed checks availability and moves physical stock directly — one transaction, no reservation row. Applying the online path to counter sales would litter the ledger with paired reserve/release entries that describe nothing.

D11

A location column exists from day one, hidden in the UIDecided

You have one location and the UI will not mention it. But retrofitting location_id into stock levels, cost layers and the transaction ledger after a year of data is a genuinely painful migration, whereas carrying one seeded row now costs nothing. This is the one place I am deliberately building ahead of the requirement.

D12

Completed purchases can only be cancelled if untouchedDecided

If any unit from a purchase has already been sold, reversing that purchase would leave sales consuming layers that no longer exist. Cancellation is permitted only while every layer from that purchase is fully unconsumed; otherwise the correct instrument is a stock adjustment or a supplier return, and the API says so in the error.

03

Proposed architecture

Four projects, ten modules, one deployable unit. The only structural rule is that dependencies point inward.

Why there is no repository layer

Application services take IAppDbContext and write LINQ directly. A generic IRepository<T> over EF Core wraps an abstraction in a near-identical abstraction, then forces awkward workarounds the moment a query needs a join or a row lock — which the FIFO consumer needs on its first line. The interface exists so Application does not reference Infrastructure and so tests can swap the context; that is all the indirection this system earns.

Module map

Each module is a folder inside Application and Infrastructure, not a separate project. Cross-module calls go through a service interface, never through another module’s internal types.

The relationships that carry weight

  • products 1—N product_variants — and every inventory relationship hangs off the variant, never the product. There is no such thing as product-level stock in this system.
  • product_variants 1—1 stock_levels per location and 1—N inventory_transactions. The one-to-one row is a cache of the one-to-many ledger, and can be rebuilt from it.
  • inventory_cost_layers N—N inventory_transactions, resolved through inventory_cost_consumptions. This join table is the heart of FIFO: it is what lets you ask, two years later, exactly which ₹500 bag left the shelf on which order.
  • orders 1—N order_items 1—N return_items — a return always points at the original line, so returned quantity can never exceed what was sold on it.
  • orders 1—N payments, summed into amount_paid. No route in the API writes payment_status.

Core schema, where correctness is enforced

The rules that must never break are written as database constraints, not as C# validation. Application code can have bugs; a check constraint cannot be bypassed by one.

stock_levels — the fast-read projection

create table stock_levels (
  variant_id    bigint  not null references product_variants(id),
  location_id   int     not null references locations(id),
  physical_qty  integer not null default 0,
  reserved_qty  integer not null default 0,
  available_qty integer generated always as (physical_qty - reserved_qty) stored,
  updated_at    timestamptz not null default now(),
  primary key (variant_id, location_id),
  constraint ck_physical_non_negative check (physical_qty >= 0),
  constraint ck_reserved_non_negative check (reserved_qty >= 0),
  constraint ck_reserved_within_physical check (reserved_qty <= physical_qty)
);

Available stock is a generated column, so it cannot disagree with its inputs — there is no code path that computes it. The three checks are the negative-stock guarantee: any bug that tries to drive physical below zero, or reserve more than exists, aborts its whole transaction at the database rather than writing a number nobody notices for a month.

inventory_cost_layers — the FIFO queue

create table inventory_cost_layers (
  id            bigserial primary key,
  variant_id    bigint  not null references product_variants(id),
  location_id   int     not null references locations(id),
  source_type   smallint not null,        -- OpeningStock | Purchase | ReturnRestock | AdjustmentIn
  source_id     bigint  not null,
  received_at   timestamptz not null,
  original_qty  integer not null check (original_qty > 0),
  remaining_qty integer not null check (remaining_qty >= 0),
  unit_cost     numeric(18,4) null check (unit_cost >= 0),   -- null = cost not known yet
  created_at    timestamptz not null default now(),
  constraint ck_remaining_within_original check (remaining_qty <= original_qty)
);

-- partial index: only open layers are ever scanned by the FIFO consumer
create index ix_layers_fifo on inventory_cost_layers
  (variant_id, location_id, received_at, id) where remaining_qty > 0;

Ordering is (received_at, id), not id alone — a purchase entered late but dated earlier still takes its rightful place at the front of the queue. The tiebreaker on id makes the order total and deterministic, which is what lets the FIFO tests assert exact results.

inventory_cost_consumptions — the audit trail that makes returns possible

create table inventory_cost_consumptions (
  id                       bigserial primary key,
  cost_layer_id            bigint not null references inventory_cost_layers(id),
  inventory_transaction_id bigint not null references inventory_transactions(id),
  order_item_id            bigint null references order_items(id),
  quantity                 integer not null check (quantity > 0),
  reversed_qty             integer not null default 0 check (reversed_qty >= 0),
  unit_cost                numeric(18,4) null,      -- copied from the layer at consumption time
  total_cost               numeric(18,2) null,
  consumed_at              timestamptz not null,
  constraint ck_reversed_within_quantity check (reversed_qty <= quantity)
);

Cost is copied onto the consumption row rather than joined from the layer, so that editing a price next year cannot rewrite last year’s profit. Optional costs need one narrow exception to that freeze: filling in a cost for a layer that has already been consumed must repair the rows it produced, or every sale drawn from it stays unknown forever.

Backfilling a cost — the only write that reaches an existing consumption row

update inventory_cost_layers
   set unit_cost = @cost where id = @layerId and unit_cost is null;

update inventory_cost_consumptions
   set unit_cost = @cost, total_cost = round(quantity * @cost, 2)
 where cost_layer_id = @layerId and unit_cost is null;   ← the safety property

Both statements are guarded by is null. A cost that was once known stays frozen exactly as originally designed; only unknowns can ever be filled. History repairs forward and is never rewritten — and because the guard lives in the where clause rather than in application code, a double-submitted backfill is harmless.

inventory_transactions — the append-only ledger

create table inventory_transactions (
  id             bigserial primary key,
  variant_id     bigint not null references product_variants(id),
  location_id    int    not null references locations(id),
  type           smallint not null,   -- OpeningStock Purchase Sale Return Damage Loss
                                  -- PersonalUse Adjustment Reservation ReservationRelease
  physical_delta integer not null default 0,   signed
  reserved_delta integer not null default 0,   signed
  unit_cost      numeric(18,4) null,
  total_cost     numeric(18,2) null,
  reference_type smallint null,       -- Order OrderItem Purchase Return ImportBatch
  reference_id   bigint null,
  reason         text null,
  notes          text null,
  occurred_at    timestamptz not null,
  created_by     bigint null references users(id),
  created_at     timestamptz not null default now()
);

Carrying both deltas on one row is what keeps reservation and consumption in a single ledger. A Reservation writes physical 0, reserved +5; a Sale writes physical −5, reserved −5; a Damage writes physical −2, reserved 0. One table, one timeline, one place to answer “where did those bags go?”

The two invariants everything else rests on

For every variant and location: SUM(physical_delta) = stock_levels.physical_qty and SUM(reserved_delta) = stock_levels.reserved_qty. Independently: SUM(layer.remaining_qty) = stock_levels.physical_qty. A GET /inventory/reconciliation endpoint checks both across the whole catalogue and names any variant that fails. Integration tests assert them after every scenario, so a drift bug fails a test rather than surfacing as a wrong profit number six months on.

Sequence allocation

Order and purchase numbers come from a row-locked counter, not from MAX(id) + 1, which races and reuses numbers after a rollback.

update number_sequences
   set next_value = next_value + 1
 where key = 'order'
returning prefix, next_value - 1;   -- ORD + 000001 → ORD-000001
06

FIFO costing

Every receipt of goods opens a layer. Every sale consumes layers oldest-first and writes down exactly what it took. Your worked example, as the system actually records it:

The consumption algorithm

ConsumeFifo(variantId, locationId, qty, transactionId, orderItemId):

  layers = select id, remaining_qty, unit_cost
             from inventory_cost_layers
            where variant_id = @v and location_id = @l and remaining_qty > 0
            order by received_at, id
              for update          ← row locks held to end of transaction

  remaining = qty
  foreach layer in layers:
      take = min(layer.remaining_qty, remaining)
      layer.remaining_qty -= take
      insert inventory_cost_consumptions(layer.id, transactionId, orderItemId,
             take, layer.unit_cost, round(take * layer.unit_cost, 2))
      remaining -= take
      if remaining == 0: break

  if remaining > 0:
      throw InsufficientCostLayersException   ← invariant broken; roll everything back

  return sum(total_cost)

The for update is not optional. Without it, two concurrent completions read the same open layers, each believes it can take ten units, and both write consumptions against stock that only one of them has. With it, the second transaction waits and then re-reads the truth. You are one user today, but a double-clicked Complete button is two concurrent requests.

When a layer has no cost

An uncosted layer is consumed like any other. The algorithm above takes its units, decrements remaining_qty and writes a consumption row — with unit_cost and total_cost left null. Nothing about the sale is blocked, because a missing cost is a bookkeeping gap, not a stock error.

What must not happen is the null quietly becoming a zero. SUM(total_cost) in SQL skips nulls, so a naive query returns a cost of goods sold that looks complete and is not — and understated cost reads as profit. Every money aggregate therefore returns a coverage figure beside it: units costed, units uncosted. A profit report is only ever as true as its coverage, and this design puts that number next to the answer rather than in a footnote.

Gross profit          ₹42,180
Revenue               ₹98,400   ·  312 units
COGS                  ₹56,220   ·  265 units costed
                                47 units uncosted  →

That arrow links to Missing costs: every layer with a null cost, newest first, with its source, quantity and one field to fill. It is what makes an optional cost recoverable rather than permanently lossy, and it is the reason the field can safely be optional at all.

Reversing a return

A return does not open a layer at today’s cost. It walks the original consumption rows for that order line in reverse order and gives the units back where they came from:

ReverseFifo(orderItemId, qty):

  rows = select * from inventory_cost_consumptions
          where order_item_id = @oi and (quantity - reversed_qty) > 0
          order by id desc       ← last consumed, first returned
            for update

  remaining = qty
  foreach row in rows:
      take = min(row.quantity - row.reversed_qty, remaining)
      row.reversed_qty += take
      layer(row.cost_layer_id).remaining_qty += take
      cogsReversed += round(take * row.unit_cost, 2)
      remaining -= take
      if remaining == 0: break

  return cogsReversed        credited to the order, and to the period’s COGS

Return two of the twelve bags above and ₹1,100 is credited — the ₹550 units, because those were consumed last. Both units land back in layer #2 with their original received_at, so they keep their true place in the queue rather than jumping to the front or the back.

07

Inventory reservation

Reservation protects stock you have promised but not yet handed over. Physical stock does not move until it physically moves.

The overselling guard

Availability is not checked and then written. It is checked in the write, as one statement, so no other transaction can slip between the two:

update stock_levels
   set reserved_qty = reserved_qty + @qty,
       updated_at   = now()
 where variant_id  = @variantId
   and location_id = @locationId
   and physical_qty - reserved_qty >= @qty;   ← the guard lives inside the write

-- 0 rows affected ⇒ not enough available stock
--                 ⇒ roll back the transaction, return 409 with the shortfall

A read-then-write pattern here would be a classic oversell: two requests both read available = 5, both reserve 5, and you have promised ten bags you do not own. The single-statement form makes that impossible, and the ck_reserved_within_physical constraint catches anything that somehow gets past it.

One transaction per operation

Confirming an order writes reservation rows for every line, updates every stock level, appends every ledger entry, records the status change and bumps the order — inside a single explicit BEGIN…COMMIT. If line four has insufficient stock, lines one through three are never reserved. The same applies to purchase completion, order delivery, return processing and the opening-stock import commit. There is no operation in this system that leaves inventory half-moved.

Payment status, always derived

paidIn   = SUM(payments where direction = In)
refunded = SUM(payments where direction = Refund)
netPaid  = paidIn - refunded

if refunded > 0 and netPaid <= 0        → Refunded
if refunded > 0                          → PartiallyRefunded   ← added, see D8
if netPaid >= order.total_amount         → Paid
if netPaid > 0                           → PartiallyPaid
otherwise                                 → Pending

Recomputed inside the same transaction as any payment insert, update or delete. Your example — a ₹3,000 order paid ₹1,000 by UPI and ₹2,000 in cash — lands on Paid without anyone selecting it. A COD order sits on Pending right through Delivered until the courier remits, which is the honest picture.

Delivery plan — two releases

Revised 24 August. Inventory management ships and goes live on its own; sales and the financial dashboard follow as a second release against the same database.

What the re-sequencing changes

Nothing in the schema, the architecture or the FIFO design. All 27 tables are created in Release 1’s first migration, including the order, payment and return tables that sit empty until Release 2. Splitting delivery does not split the database — a half-built schema would force a painful migration the moment orders arrive.

What does change is order of work, and two things move earlier: the opening-stock import and the production deployment. Both were near the end of the original plan; both are now inside Release 1, because a stock system you cannot load your existing stock into and cannot reach from your phone is not usable.

Release 1 — Inventory management

The goal is a system you actually run the stock side of your business on, deployed and holding real data, before any order code exists. Reserved stock stays at zero throughout and the reservation columns sit unused — by design, not by omission.

Test coverage at the gates

Unit tests run against the Domain layer with no database, and carry most of the load. Integration tests run against a real Postgres — the test schema of the same Supabase project — because half the guarantees in this design are database constraints and an in-memory provider would not enforce a single one of them.

That schema is created and dropped on every run, so the fixture is guarded: it reads the connection string and refuses to start unless the search path is test. DROP SCHEMA test CASCADE cannot reach public, which is what makes it safe to run destructive tests against the same database that holds real stock. Because every statement is a network round trip, integration tests are kept few and load-bearing — FIFO consumption, the oversell race, import rollback, the invariants — and everything else is a unit test.

Both questions that gated this design are answered. GST is out of scope for both releases, which removes fields rather than adding them.
